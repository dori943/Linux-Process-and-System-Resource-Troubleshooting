# [Bug] CPU Spike - CpuWorker 부하 상승으로 Watchdog 이 SIGTERM 으로 프로세스 종료

> **심각도**: High | **유형**: CPU Spike / Watchdog | **상태**: 분석 완료

## 1. Description (현상 설명)

- **무슨 일이 발생했는가?** `agent-leak-app` 을 실행하면 약 38초 뒤 `CPU Threshold Violated!` 로그와 `WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM)` 배너가 출력되고 프로세스가 종료된다. 종료 코드 143 (128+15 = SIGTERM).
- **언제, 어떤 조건에서?** `CPU_MAX_OCCUPY=80` (50 초과) 로 실행할 때 매번 재현된다. 앱이 보고하는 `Current Load` 가 5% 에서 3초마다 상승해 약 50% 를 넘는 순간 종료된다.

실행 환경 (Before):
```
MEMORY_LIMIT=512
CPU_MAX_OCCUPY=80
MULTI_THREAD_ENABLE=false
실행 시각: 2026-10-21 20:35:09   워커 PID: 1005
```

## 3. Root Cause Analysis (원인 분석)

**현상 분석.** `CpuWorker` 는 시작 후 부하를 계단식으로 올린다 (5% → … → 50%+). 부팅 로그의 `[CPU] Limit: 80% [WARNING: Recommend Under 50%]` 가 말하듯, 50 을 초과하는 설정은 앱이 "위험 구성" 으로 분류한다. 이 구성에서는 Load 가 약 50% 를 넘는 순간 `CPU Threshold Violated!` 를 남기고 Watchdog 이 SIGTERM 을 보낸다.

**이것은 오류가 아니라 보호 조치다.** 근거는 세 가지다. (1) 종료 직전 로그가 Traceback 이 아니라 CRITICAL 레벨의 임계치 위반 메시지다. (2) 터미널에 `WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM)` 배너가 찍힌다. (3) 종료 코드가 143 = 128 + SIGTERM(15) 이다. 메모리 보호가 SIGKILL(즉시 제거)을 쓰는 것과 달리 CPU 보호는 SIGTERM(정리 후 종료 요청)을 쓴다. CPU 과점유는 당장 자원을 회수하지 않아도 시스템이 죽지 않으므로 graceful shutdown 기회를 준다.

**OS 동작 원리.** CPU 는 코어당 한 번에 한 스레드만 실행한다. 항상 실행 가능(R) 상태인 프로세스가 있으면 런큐가 길어지고(load average 상승) 다른 프로세스는 타임슬라이스를 기다리며 응답이 늦어진다. 컨텍스트 스위칭 비용도 늘어난다. 앱이 시작 시 `nice=10` 으로 우선순위를 낮추는 것도 같은 이유의 완화책이다(CFS 스케줄러가 nice 가 높은 프로세스에 CPU 시간을 덜 배분).

## 4. Workaround & Verification (조치 및 검증)

**조치.** `CPU_MAX_OCCUPY` 만 80 → 30 으로 하향해 재실행했다.

```bash
export CPU_MAX_OCCUPY=30   # Before: 80
```

**Before & After (실측).**

| 구분 | 환경변수 | 생존 시간(초) | 결과 | 종료 코드 | 최대 RSS(MB) |
|---|---|---|---|---|---|
| Before | MEMORY_LIMIT=512, CPU_MAX_OCCUPY=80, MULTI_THREAD_ENABLE=false | 38 | 스스로 종료 | 143 (128+15, SIGTERM) | 17.6 |
| After | MEMORY_LIMIT=512, CPU_MAX_OCCUPY=30, MULTI_THREAD_ENABLE=false | 50+ (관찰 종료 시점까지 생존) | 관찰 종료까지 생존 (수동 kill) | - (종료 안 됨) | 392.9 |

마지막 로그 한 줄:

- Before: `2026-10-21 20:35:45,905 [CRITICAL] [CpuWorker] CPU Threshold Violated! (50.25%).`
- After: `2026-10-21 20:36:51,285 [INFO] [MemoryWorker] Current Heap: 500MB`

종료 배너(터미널 출력):

- Before: `>>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<`
- After: `>>> [SYSTEM] ALL CONFIGURATIONS OPTIMAL. RUNNING STABILITY TEST... <<<`

**해석.** 80 에서는 38초 만에 SIGTERM 으로 종료됐지만, 30 에서는 Load 가 30% 에 닿으면 `Peak reached. Starting cooldown...` 후 5% 까지 내려갔다 다시 오르는 사이클을 반복하며 종료되지 않는다. 임계치를 낮추면 Watchdog 이 "종료" 대신 "쿨다운" 으로 대응할 여유가 생긴다. 근본 해결은 부하 로직에 상한을 두거나 cgroups `cpu.max` 로 OS 레벨에서 CPU 시간을 제한하는 것이다.
